## Unreleased — macOS Metal render path (Apple Silicon)

Not a release and not yet run in Resolve on a Mac. The version number is assigned when this merges with the macOS CPU build (W1).

- New Metal render path for macOS, built only with `-DNSS_METAL` and `ofx/src/metal_render.mm` (Objective-C++, ARC). Windows and Linux builds do not compile or link any Metal code; the Win64 binary still imports only KERNEL32 and msvcrt.
- Describe declares `kOfxImageEffectPropMetalRenderSupported` next to the CUDA/OpenCL flags: `true` when a Metal device exists, otherwise `false`. `Render engine = CPU` clears it on the instance, the same as CUDA/OpenCL.
- Render uses the host's `kOfxImageEffectPropMetalCommandQueue` and the host's `MTLBuffer` images directly (zero copy on unified memory). One compute dispatch is encoded and committed without `waitUntilCompleted`; the host orders its later work on the same queue. Parameters go in with `setBytes`.
- The kernel source is embedded (`metal_source.hpp`, generated by `tools/generate.py` from `render_math.h` and `render.metal`) and compiled at run time once per `MTLDevice` with fast math off (`fastMathEnabled = NO`; on macOS 15 also `mathMode = safe` and precise math functions) and `metal::precise` functions. The compute pipeline is cached per device (keyed by registry ID).
- The only change to the shared math for Metal is the `thread` address space on the three pointer parameters of `nss_tone_color`; `check_metal_source.py` proves the embedded copy is otherwise `render_math.h` byte for byte. Core math is unchanged.
- Threadgroup size comes from the pipeline (`threadExecutionWidth` x `maxTotalThreadsPerThreadgroup / threadExecutionWidth`); no per-chip constants.
- Any Metal failure (no device, compile, pipeline, bad buffer layout, encode error, exception, or an asynchronous command-buffer error reported by the completion handler) never fails describe, createInstance or the frame: the instance withdraws Metal (`kOfxImageEffectPropMetalRenderSupported = false`) and renders the frame on the CPU in place on the shared buffers after one queue drain. Only GPU-private buffers, which the CPU cannot reach, report `kOfxStatGPURenderFailed`.
- The viewer gray picker reads the source from the shared buffer after one queue drain, as the CUDA/OpenCL pickers already sync for their small patch.
- macOS only: the **Rendering** group is visible, with `Render engine` (choices exactly `Auto (Metal)` and `CPU`) and the `Show render engine` button, so Metal and CPU can be compared in Resolve. Auto renders with Metal when the host offers it, otherwise on the CPU; CPU withdraws the Metal flag. Choice indices are unchanged on every platform (0 = Auto, 1 = CPU), so saved projects keep their meaning; the Windows label `Auto (CUDA/OpenCL if offered)` and the macOS label `Auto (Metal)` are the same index 0.
- macOS `Show render engine` reports the last render first, `Metal (<GPU name>), host queue buffers` or `CPU <n> threads` (with the fallback reason if Metal failed), then the Metal state (device and unified memory, or why Metal is off). Windows and Linux keep the 0.90.14 text (last render, CUDA and OpenCL lines).
- Windows and Linux: Rendering controls stay hidden with the 0.90.14 labels, choices and defaults. `test.sh` proves it: `param_dump.cpp` prints every parameter definition and `check_param_defs.py` requires the Windows/Linux and macOS variants to be identical except visibility, the Auto label and hints of the three Rendering entries (the Windows/Linux dump was also byte-identical to the 0.90.14 base, bd0de46, when this was added). Parameter names are checked unique.
- Tests: `test.sh` adds `check_metal_source.py`, `metal_contract.cpp` (built twice: Windows/Linux UI and macOS UI) and the per-platform parameter check (mocked Metal API plus the exact embedded kernel compiled as host C++: worst abs 0 vs the CPU on 5 variants; property declare/withdraw, no-wait encode, CPU fallback on 5 forced failures, async error, private buffers, CPU engine, picker). New CI workflow `.github/workflows/macos-metal.yml` (macos-15 and macos-26, arm64; the macos-14 label was retired on 2026-11-02) builds the Metal bundle and runs `metal_plugin_test.cpp` on the real Metal device: Metal vs CPU parity (limit 1e-4), one pipeline build per device, forced failures that do not poison the cache, and plugin-level CPU fallback.
- Forced-failure test hooks live only in test builds compiled with `-DNSS_TEST_HOOKS`. A release Mac binary is checked (`ofx/tests/check_release_hooks.py`) not to contain `Metal encode failed (forced by test)` or the other hook strings. CI still runs the forced-failure fallback test against a separately compiled test object.
- Minimum macOS is 13.0: `-mmacosx-version-min=13.0` and `LSMinimumSystemVersion` 13.0 in `ofx/mac/Info.plist.in`, stamped with the plugin version by `ofx/build-mac.sh` (the Metal CI builds with it; the placeholder `ci/macos/Info.plist` is retired). CI checks both the plist and the Mach-O minos.
- Known limits: the CPU fallback and the picker wait for the host queue (rare paths only). Real Resolve on a Mac, real Apple GPU speed and the ad-hoc signed bundle install are untested.

## 0.90.14 — Separate Tone Color group with switches and presets, stronger cream after desaturation

- UI: the color controls are a new, separate **Tone Color** group. Each group is laid out as switches, then its own preset menu, then the sliders:
  - **Tone**: `Highlight shoulder`, `Shadow toe` (switches) -> `Tone preset` -> `Shoulder strength`, `Shoulder start (stops)`, `Shoulder white (stops)`, `Toe strength`, `Toe start (stops)`, `Toe black (stops)`.
  - **Tone Color**: `Highlight desaturation`, `Highlight cream`, `Shadow desaturation` (switches, new) -> `Tone color preset` (new) -> `Highlight desaturation amount`, `Highlight color start (stops)`, `Highlight cream amount`, `Shadow desaturation amount`, `Shadow color start (stops)`.
- `Tone preset` loads only shoulder/toe; `Tone color preset` loads only the color group. Editing a switch or slider sets only its own group's menu to `Custom`. Switch off renders bit for bit like amount 0.
- Tone color presets: `Soft cinematic` (default; 0.60 / +0.75 / 1.00, shadow 0.70 / -2.00), `Gentle` (0.40 / +1.00 / 0.60, 0.40 / -2.25), `Strong` (0.75 / +0.50 / 1.00, 0.80 / -1.75), `Night practicals` (0.50 / +1.00 / 0.80, 0.50 / -2.50), `Off` (all three switches off), `Custom`. Tone presets unchanged except that they no longer carry color values.
- Existing 0.90.12/0.90.13 projects: the new switches default ON, the old single Tone preset index now drives shoulder/toe only, and the new color menu starts at `Soft cinematic`.
- Cream now runs **after** highlight desaturation and is measured on the desaturated pixel, so desaturation can no longer cancel it: with `Highlight desaturation amount` 1 the top highlights become warm cream with cream on and exactly neutral (R = G = B) with cream off.
- Cream is stronger and warmer: R, G, B are multiplied by `(1 + a, 1, 1 - 0.3a)` with `a = 0.40*cream*w_h*max(1 - 2*saturation, 0)^2` (0.90.13: `(1 + a, 1 + a/4, 1 - a)`, `a = 0.15*cream*w_h*(1 - saturation)^2`), then rescaled so Rec709 `Y` is unchanged. It fades out completely at HSV saturation 0.5, so sky and practicals keep their hue (max 15 degrees HSV move for saturation above 0.3, was 19).
- Region weight is now a smoothstep over 1.5 stops past each color start (`u = clamp(t/1.5, 0, 1)`, `w = u^2(3 - 2u)`), still C1 at the start, but it reaches full strength (0.90.13's `t^2/(1+t^2)` never reached 1, so amount 1 never fully desaturated). Applies to highlight and shadow desaturation and to cream.
- New default measured through the repo `Kodak_2383_D65` LUT with per-frame gray-world balance (frames 0280 / 0206 / F2 / F5), top 1% RGB: 210/200/187, 207/203/198, 206/196/190, 213/205/201 (0.90.13: 0206 205/203/199, F5 208/207/204; color off: 0206 203/202/204, F5 206/207/210; reference Silbersalz35 graded 197/191/188). Top 1% saturation 0.110/0.063/0.079/0.056; mid-tone luminance unchanged on 0206/F2/F5. Highlight desaturation 1 with cream on: 0206 211/202/191, F5 217/204/194; with cream off: 0206 203/204/196, F5 206/207/202 (the residual blue dip is the 2383 LUT's own rendering of neutral highlights).
- Defaults otherwise equal 0.90.13 (desaturation 0.60 from +0.75, cream 1.00, shadow 0.70 from -2.00), but the default look is warmer because cream and the region weight changed.
- Tests: `tone_test.cpp` adds desaturation 1 + cream off = neutral and + cream on = warm (R > G > B, (R-B)/R >= 0.05) above the highlight start; all earlier tone checks pass (off = 0.90.11 and color zero = 0.90.12 bit for bit, kernel vs reference worst 7.2e-7, ramps, hue, cream only above start, desaturation only in the tails). Host test checks the two groups, definition order, per-group presets and per-group Custom. PoCL OpenCL runs 9 tone/color preset pairings on every output (344 cases, max abs 8.4e-5). PTX regenerated (NVRTC 12.0.140, 18 registers, no spills). Plugin label **NegativeScan Studio OFX 0.90.14**, version minor 9014.
- Known limits: not yet run in Resolve or on a real GPU. A viewer gray pick on a bright patch looks cream when Highlight cream is on (by design). The 2383 LUT still renders neutral blacks cyan and neutral highlights slightly yellow.

## 0.90.13 — Tone: highlight and shadow desaturation, highlight cream (local test build)

- New controls in the **Tone** group (English only): `Highlight desaturation`, `Highlight color start (stops)`, `Highlight cream`, `Shadow desaturation`, `Shadow color start (stops)`. They are part of every preset and edits switch the menu to `Custom`.
- **Default ON** in `Soft cinematic`. Preset values:

| Preset | Highlight desaturation / color start (stops) / cream | Shadow desaturation / color start (stops) |
|---|---|---|
| **Soft cinematic** (default) | 0.60 / +0.75 / 1.00 | 0.70 / -2.00 |
| Gentle | 0.40 / +1.00 / 0.60 | 0.40 / -2.25 |
| Strong roll-off | 0.75 / +0.50 / 1.00 | 0.80 / -1.75 |
| Night practicals | 0.50 / +1.00 / 0.80 | 0.50 / -2.50 |
| Off / Classic 0.90.11 | 0 / +0.75 / 0 | 0 / -2.00 |

- Runs after the 0.90.12 shoulder and toe, on scene-linear values, before the output encoding (all five outputs). Region weight from the RGB mean in stops, `x = log2(mean/0.18)`: highlight weight `w(x - start)`, shadow weight `w(start - x)`, `w(t) = t^2/(1+t^2)` for `t > 0`, else 0. The weight fades in with zero slope (C1); nothing between the shadow and highlight color starts changes. The shadow start is never above the highlight start.
- Desaturation mixes each pixel toward its own Rec709 luminance `Y`: `c' = c + (hd*w_h + sd*w_s)*(Y - c)`. `Y` and HSV hue are unchanged; values stay non-negative.
- Cream multiplies R, G, B by `(1 + a, 1 + a/4, 1 - a)` with `a = 0.15*cream*w_h*(1 - saturation)^2`, then rescales so `Y` is unchanged. Neutral highlights turn warm cream; saturated highlights (sky, practicals) keep their hue (at most about 19 degrees HSV move for saturation above 0.3). Mid-tones and shadows get no tint.
- Luminance is unchanged by the color stage, so luminance ramps behave exactly as in 0.90.12.
- Off: all three strengths 0 gives output bit-identical to 0.90.12 (checked against a d969a3f build on 1.9 million values for every preset and output); all Tone off still equals 0.90.11.
- Constants grew from 48 to 56 floats; PTX regenerated (NVRTC 12.0.140, 19 registers, no spills).
- Measured through the repo `Kodak_2383_D65` LUT with a per-frame gray-world balance (frames 0280 / 0206 / F2 / F5): top 1% saturation 0.117/0.083/0.071/0.031 -> 0.112/0.064/0.068/0.025, top 1% RGB of 0206 203/202/204 -> 205/203/199 and F5 206/207/210 -> 208/207/204 (reference Silbersalz35 graded 197/191/188), bottom 5% saturation 0.746/0.718/0.502/0.834 -> 0.709/0.713/0.449/0.691. Mid-tone luminance unchanged on 0206/F2/F5; the bright 0280 frame rises from 137 to 143 because its mid-tones reach the highlight region.
- Known limits: the 2383 LUT itself renders neutral blacks cyan (about 11/16/18 of 255), which dominates output shadow saturation, so shadow desaturation removes scene color but cannot neutralize the LUT's black. A viewer gray pick on a bright patch will look slightly cream when Highlight cream is on (by design). Real Resolve and real GPU testing are pending.
- Tests: `tone_test.cpp` adds color-zero = 0.90.12 bit-for-bit, luminance kept by the color stage, luminance-monotonic hue-line ramps, cream only above the highlight start, desaturation only in the tails, neutral highlights warm, bounded hue move; host test covers the new parameters and presets; PoCL OpenCL runs every preset (all Tone keys); Go parity with Tone off. Plugin label **NegativeScan Studio OFX 0.90.13**, version minor 9013.

## 0.90.12 — Tone: highlight shoulder and shadow toe (local test build)

- New open **Tone** group (English only) with `Tone preset`, `Highlight shoulder` (on/off), `Shoulder strength`, `Shoulder start (stops)`, `Shoulder white (stops)`, `Shadow toe` (on/off), `Toe strength`, `Toe start (stops)` and `Toe black (stops)`. Choosing a preset writes the eight controls; editing any of them switches the menu to `Custom`.
- **Default is ON** with `Soft cinematic`, so new instances render soft, non-clipping highlights and lifted, slightly desaturated blacks. Choose `Off / Classic 0.90.11` (or switch both off) for output that is bit-identical to 0.90.11. Existing projects that were saved without these parameters get the new default when opened.
- Presets:

| Preset | Shoulder on / strength / start / white (stops) | Toe on / strength / start / black (stops) |
|---|---|---|
| **Soft cinematic** (default) | on / 1.00 / +0.75 / +2.20 | on / 1.00 / -2.00 / -4.00 |
| Gentle | on / 0.60 / +1.00 / +2.60 | on / 0.60 / -2.00 / -3.80 |
| Strong roll-off | on / 1.00 / +0.50 / +1.80 | on / 1.00 / -1.75 / -3.60 |
| Night practicals | on / 1.00 / +1.00 / +2.40 | on / 0.50 / -2.50 / -4.00 |
| Off / Classic 0.90.11 | off | off |

- Tuned offline on four frames (Hikrobot mono trichrome HDR 0280, X-T3 0206, X-T3 500T F2 and F5) through the repo `Kodak_2383_D65` LUT toward the Silbersalz35 graded reference (Y p0.5/p50/p99.9 = 14/133/198, no clipping). With a per-frame gray-world balance, `Soft cinematic` gives top 202/205/205/209, black 19/25/21/19, mids 137/137/127/100 (0.90.11: top 244/247/235/246, mids 147/137/127/100) and 0% pixels above 250. See `docs/OFX.md`.
- Math (identical in CPU, OpenCL and CUDA; shared `render_math.h`):

- Where: on the scene-linear positive of the Positive stage, after the per-channel inversion and the optional `Contrast` curve, and before the output encoding. The Density In stage and transmittance output are never toned. Stops are `log2(value / 0.18)`, so they move with `Exposure` and the balances.
- Shoulder (highlights): `n = mean(R,G,B)`, `x = log2(n/0.18)`. Above `start` (`xs`), `f = xs + h*(1 - exp(-(x - xs)/h))` with `h = white - xs` (at least 0.05), then `y = x + strength*(f - x)`. R, G and B are multiplied by the same gain `2^(y - x)`, so R:G:B ratios and hue are unchanged. At full strength the mean never goes above `white`, so with the default preset the brightest channel is at most about `+3.8` stops (3x the mean; Cineon about 800 of 1023): nothing clips in Cineon or in a 0..1 LUT input.
- Toe (shadows): `m = min(R,G,B)` after the shoulder, `x = log2(m/0.18)`. Below `start` (`xt`, never above the shoulder start), `g = xt - r*(1 - exp(-(xt - x)/r))` with `r = xt - black` (at least 0.05), and the same offset `strength*(0.18*2^g - m)` is added to R, G and B. Hue (HSV) is unchanged, deep shadows desaturate slightly, and pure black lifts to the neutral floor `strength*0.18*2^black` (default 0.0113 linear, Cineon about 187 of 1023). The darkest channel is used, not the mean, because an offset from the mean makes the weakest channel of saturated dark colors go backwards; with the darkest channel every channel is monotonic along any hue line.
- Both curves have slope 1 at their start point (C1, no kink), are monotonic, and leave everything between the toe start and the shoulder start untouched.
- Output encodings: the tone runs on scene-linear values, so Rec709, DaVinci Intermediate, Cineon, ACEScct and Linear all receive the same toned linear values through their unchanged encoders. With Linear output the shoulder keeps values below `0.18*2^white` times the pixel's max/mean ratio (at most 3x); with Rec709 values above 1.0 are still possible for very bright saturated pixels, exactly as in 0.90.11.
- Density clamp: the 1.856 density cap (`Clamp output to 0 to 1`) is unchanged. No pixel of the four test frames reaches it (the brightest Cineon values come from the positive curve, not the cap), so softening it was not needed.
- Off: when both switches are off (or both strengths are 0) the kernels take the 0.90.11 per-channel code path, bit for bit (checked against a 0.90.11 build on 3.1 million values: identical).
- Constants grew from 40 to 48 floats (`Prepared`, OpenCL `__constant`, CUDA `NssBlock`). PTX regenerated with NVRTC 12.0.140 (`docs/data/ofx_0902_cuda_build.json`). Presets live in `docs/data/ofx_tone_presets.json`; `ofx/tools/generate.py` writes `ofx/src/tone_params.hpp` and the parameter plumbing from it.
- CPU fallback cost on a real 500T frame (0206, single thread): 73 ns/pixel off, 100 ns/pixel with `Soft cinematic`. GPU kernels add the same few operations per pixel; no real GPU timing was done.
- Tests: new `ofx/tests/tone_test.cpp` (off = 0.90.11 path bit for bit for all outputs and contrasts, kernel math vs an independent stops-based reference, 16-bit ramps, hue drift on saturated patches, no Cineon clipping, C1 at both pivots, black floor); host test (version 9012, defaults, visible controls, preset application, `Custom`); PoCL OpenCL parity for every preset and output; mocked CUDA contract with the default tone; Go parity with Tone off.
- Known limit: on a gray input ramp the channels drift apart in the densest highlights (the stock gammas differ per channel), and because the shoulder keeps R:G:B, the weakest channel can dip by up to 0.15 stops (`Soft cinematic`; 0.20 for `Strong roll-off`) above about +5 stops. Luminance stays monotonic.
- Plugin label is **NegativeScan Studio OFX 0.90.12**; version minor is 9012. No other defaults, parameters or inversion math changed. Real Resolve and real GPU testing are still pending.
